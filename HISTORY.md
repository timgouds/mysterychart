# Chart Game — data sources & foundational decisions

_Last updated: 25 Aug 2026_

## What we're building

A daily "guess the chart" game, inspired by [Chartle](https://chartle.cc/) (guess the country in red)
and [Charted](https://chartedgame.com/) (multiple choice, a hint after each wrong answer).

Ours differs in two ways:
- The chart can be **any shape** — line, stacked column, scatter, area — not always the same format.
- Questions are **multiple choice**, and each wrong answer reveals a **hint**.

Tim has no coding experience, so everything is built with explanation as we go.

## Decisions made (25 Aug 2026)

| Decision | Choice |
|---|---|
| Data theme | World & society statistics (health, climate, energy, population, economy) |
| Format | Daily puzzle — one chart a day, same for everyone, shareable result |
| Question creation | Auto-generated by code from the data |

## Core architectural principle

**Collect data, not chart images.**

Scraping chart pictures from news sites gives a folder of images that go stale, can't be
restyled, and must be re-collected by hand forever. Instead we fetch raw numbers from public
data APIs and the game draws the chart itself. This gives:

1. Data that stays current automatically
2. Full control of visual style
3. Freedom to render the same dataset as different chart types

## Primary data source: Our World in Data

Chosen as the main source. ~5,000 curated, actively maintained charts.

- **No API key required**
- **Licence:** CC BY 4.0 — attribution required, redistribution permitted
- A small number of datasets are marked non-redistributable and return HTTP 403

### Endpoint patterns

```
https://ourworldindata.org/grapher/{slug}.csv                  # full dataset
https://ourworldindata.org/grapher/{slug}.csv?csvType=filtered&country={CODES}&time={range}
https://ourworldindata.org/grapher/{slug}.metadata.json        # units, source, description
https://ourworldindata.org/grapher/{slug}.config.json          # OWID's own chart settings
```

`{slug}` is the last part of any OWID chart URL, e.g. `life-expectancy`.
Country codes are joined with `~`. Time accepts `2015..latest`.

### Verified working (25 Aug 2026)

`GET /grapher/life-expectancy.csv?csvType=filtered&country=GBR~JPN~USA&time=2015..latest`
returned real rows, e.g.

```
Entity,Code,Year,Life expectancy
Japan,JPN,2023,84.7123
United Kingdom,GBR,2023,81.3015
United States,USA,2023,79.3043
```

The `.metadata.json` endpoint is important: it carries units, the underlying source, and a
description. That text is the raw material for **auto-generating hints**.

## Secondary sources (later phases)

| Source | Key needed | Notes |
|---|---|---|
| World Bank Indicator API | No | ~1,500 indicators, every country. Very structured — easy to auto-generate from. |
| FRED (St. Louis Fed) | Free key | 800k+ economic series, updated daily. Good for "which recession is this?" |
| Eurostat | No | European detail |
| ONS | No | UK detail |
| Wikipedia Pageviews API | No | Parked — playful/pop-culture flavour, doesn't fit the chosen theme, but a strong future expansion |

## Freshness strategy

Do **not** call the API live on every page load — slow, and breaks whenever a source has a bad day.

Instead: a **refresh script** runs on a schedule (weekly), pulls the latest numbers, and writes
them to a data file the game reads instantly. The game is then fast and reliable, and data is
never more than a week old.

## Known constraint

This Claude sandbox's network proxy blocks `ourworldindata.org` for direct shell requests
(HTTP 403 on CONNECT). Data can still be pulled here via the WebFetch tool. The production
refresh script will run in the hosting environment, not in this sandbox, so this is a
development-time inconvenience only — but it means bulk data collection here is slow and
must go one request at a time.

## Open questions for next session

1. Which chart types to support first, and how the game decides which to use for a given dataset
2. How wrong answers get generated so they're plausible but not accidentally correct
3. What a "hint" actually is — progressive reveal (axis labels → units → region → year range)?
4. Where it gets hosted, and how the daily puzzle is chosen and locked to the date

# Chart Game — game design

_Last updated: 25 Aug 2026_

Companion to `claude/01-data-sources-and-decisions.md`.

## The central reframe (Tim, 25 Aug)

**The player guesses what the chart represents, not which country is in it.**

Example: an ordered bar chart topped by Spain, Italy, Greece and Turkey — the answer is
"top olive oil producers", and the country names are the *evidence*, not the answer.

This is a bigger change than it sounds:

- **Country names stay visible.** They are the clue the player reasons from.
- **The subject is what gets hidden:** the title, the metric name, the y-axis label,
  the units, the legend heading, and the source credit.
- **The multiple-choice options become competing descriptions of the chart**, which
  means the wrong answers now carry the entire difficulty of the game.

## Playable prototype

<https://claude.ai/code/artifact/480720bc-67fd-476d-a132-778451c7fbb5>

Three puzzles, all real 2024/2025 Our World in Data figures. Visual concept: the chart is a
**redacted document** — a black bar sits where the title should be and lifts when solved.

## 1 · Choosing the chart type (FT Visual Vocabulary)

Per Tim: take chart-type guidance from the
[FT Visual Vocabulary](https://github.com/Financial-Times/chart-doctor/tree/main/visual-vocabulary).

It classifies charts by the **relationship the data expresses**, across ten families:
Deviation, Correlation, Ranking, Distribution, Change over Time, Part-to-whole, Magnitude,
Spatial, Flow, and an emerging Uncertainty group.

This is usable as code because the shape of the downloaded data determines the family:

| Shape of the data | FT family | Form we draw |
|---|---|---|
| One measure, many countries, one year | Ranking | Ordered horizontal bar |
| One measure, few countries, many years | Change over Time | Multi-line |
| Parts summing to a whole, over time | Part-to-whole | Stacked column / area |
| Two measures, many countries | Correlation | Scatterplot |
| One measure spread across a population | Distribution | Histogram / dot strip |
| Change against a baseline, +/− | Deviation | Diverging bar |
| One measure, all countries, one year | Spatial | Choropleth — **deferred**, see below |

**Maps are deferred.** A choropleth shows country outlines, which changes the puzzle from
"read the ranking" to "recognise the map", a different and much easier game. Worth adding
later as a distinct mode, not mixed into the main rotation.

Two filters run in sequence: the FT rule says which forms are *honest* for the data; a
puzzle-quality filter then picks which is the *best puzzle*.

## 2 · Decoy generation — the difficulty dial

The wrong answers determine whether a puzzle is trivial, fair, or unfair.

**The discovery that proves the mechanic:** cocoa and coffee share roughly half their
producer list (Brazil, Indonesia, Peru, Colombia, Ecuador) but rank them completely
differently.

- Cocoa 2024: Côte d'Ivoire 1.89 Mt, Indonesia 633 kt, Ghana 530 kt, Ecuador 404 kt
- Coffee 2024: Brazil 3.39 Mt, Vietnam 2.02 Mt, Colombia 840 kt, Indonesia 808 kt

Each is the other's ideal decoy. That is the target difficulty: overlapping enough to be
tempting, ordered differently enough to be decidable.

### Rules for generating decoys

1. **Same topic area, different metric.** Draw from OWID's own topic tags.
2. **Similar units and order of magnitude.** A decoy measured in % against an answer in
   tonnes is eliminated without reading the chart.
3. **Reject any decoy that is arguably also true.** "Top cocoa producers" vs "top cocoa
   exporters" would be unfair — nearly the same chart.
4. **Reject decoys that are obviously false at a glance** — an unrelated topic makes the
   puzzle trivial.

### The population-ranking test (puzzle quality)

If a ranking chart's order is roughly the population or GDP ranking — China, India, USA at
the top — then almost any metric could produce it and the puzzle is unsolvable by reasoning.
Compare the ordering against the population ranking; if correlation is above a threshold,
**reject the puzzle**. Distinctive orderings (Côte d'Ivoire first) are what make good puzzles.

### Data sanity check

Auto-generation needs a guard against bad source values. The FAO coffee figures list the
Central African Republic at 324,923 tonnes — implausibly high, and it would have appeared
9th in an auto-built top-10. The prototype uses the top 8 to sidestep it. The real version
needs an outlier check before a dataset is allowed to become a puzzle.

## 3 · Hints — cryptic and playful

Per Tim: hints should tease, not simply inform. Each wrong answer buys one, and they run
from oblique to nearly-giving-it-away.

**The ladder:**

| # | Character | Example (cocoa) |
|---|---|---|
| 1 | Riddle. Geography or history, obliquely. | "Two neighbours on the Gulf of Guinea between them supply almost half the world's appetite for this." |
| 2 | A structural clue about the subject. | "It grows only near the equator, yet the countries that eat the most of it are cold, rich and northern." |
| 3 | Units and scale. | "Measured in tonnes. The leader alone grows more than the next three combined." |
| 4 | A shove. | "It leaves the farm as a bitter bean and reaches you as a sweet bar." |

Also worth stealing from [Charted](https://chartedgame.com/): its hints are **relative to the
wrong answer just given** ("different sector, higher market cap"). Adapted here: "Warmer —
right continent, wrong crop." This makes hints feel responsive rather than canned.

### Open problem: automating wit

This is the one place where "auto-generated" degrades. Rules can produce hints 3 and 4
(units and scale come straight from the OWID metadata). Hints 1 and 2 need genuine wit.

Options:

- **(a)** Generate all four from metadata — reliable, factual, flat.
- **(b)** Use an AI model at build time to write cryptic hints for each dataset, and have
  Tim skim and reject the weak ones. A daily game needs ~365/year, so a batch of 50 at a
  time is a manageable review session. **Recommended.**
- **(c)** Hand-write for the first 50 puzzles.

Note this partially revisits the "fully auto-generated" decision in doc 01 — the cryptic
hint requirement is what changes the calculus. Decision pending with Tim.

## Design decisions in the prototype

- Chart palette follows a validated accessible scheme; the categorical palette was checked
  programmatically for colour-blind separation in both light and dark themes.
- Country names are always directly labelled — identity is never carried by colour alone,
  which matters more here than usual because the labels *are* the puzzle.
- Hovering any bar or year reveals exact values. Since the numbers are evidence rather than
  the answer, giving the player precision costs nothing and rewards close reading.

2. How the daily puzzle is chosen and locked to the date, identically for every player
3. Where it gets hosted, and what it costs
4. Whether a shareable result grid (the Wordle mechanic) is in the first version

# Chart Game — choosing chart forms

_Last updated: 25 Aug 2026_

Third doc. See also `01-data-sources-and-decisions.md` and `02-game-design.md`.

## Decisions settled this round (Tim, 25 Aug)

1. **Hint automation confirmed.** Generate cryptic hints automatically; Tim reviews them
   over time. This resolves the open question in doc 02 — option (b).
2. **Charts must be visually varied and "funky".** Static ordered bar charts of a single
   year's data are the weakest puzzles and should be rare.

## Why the bar charts were boring — the actual diagnosis

Not an aesthetic problem. An ordered bar chart of one year's figures **throws away the time
dimension**, and time is where the stories live. Coffee's 2024 ranking is a lookup; coffee's
*reordering since 1990* is a story with a protagonist.

Two rules follow:

- **Prefer forms that use time.** Snapshots earn their place only when the snapshot itself
  is startling — extreme concentration, a shocking outlier.
- **Among the honest forms, draw the one that makes the dataset's most distinctive feature
  visible on load.** The FT Visual Vocabulary narrows the field to what's valid; this rule
  picks the winner.

| Dataset | Distinctive feature | Form chosen |
|---|---|---|
| Cocoa, 2024 | Extreme concentration — one country >⅓ of world output | **Treemap** |
| Coffee, 1990 & 2024 | Violent reordering — Vietnam climbs 15 places | **Rank slope** |
| Fertility, 1970 & 2023 | Universal collapse at wildly different speeds | **Dumbbell** |
| Child mortality, 1970–2024 | Steady decline with one war-shaped cliff | **Multi-line** |

## The hard constraint: visible labels must be entities, never measures

The game only works when the **visible labels are entities** (countries, regions, years) and
the **hidden thing is the measure**.

This rules out some otherwise attractive forms. A stacked area of electricity generation
would need a legend reading coal / gas / wind / solar — which *is* the answer. Part-to-whole
works here only when the parts are places, which is why the cocoa treemap works and an
energy-mix streamgraph does not.

Worth checking every candidate form against this before adding it.

## Form catalogue, ranked for this game

**Strong — visually distinctive and reward reading:**

- Treemap (part-to-whole by country) — concentration reads instantly
- Rank slope / bump chart — reordering over time; needs no units at all, since rank is
  self-explanatory. Excellent for hiding the measure completely.
- Dumbbell — before/after per country; shows both level and change
- Connected scatterplot — two measures traced through time; the *shape of the path* is the
  clue. The funkiest available form. Not yet built.
- Beeswarm / dot strip — distribution across all countries
- Multi-line — the reliable classic; keep in rotation for contrast

**Usable:**

- Diverging bar (change against a baseline)
- Lollipop (a lighter ordered bar)
- Slope of values on a log scale
- Waterfall

**Deferred or excluded:**

- Choropleth and all maps — shows country outlines, turning the game into map recognition
- Stacked area / streamgraph by *source* — legend gives away the answer (see constraint above)
- Pie / donut — a worse treemap
- Radar — hard to read, rarely honest

## Rotation rule for the daily game

Don't repeat a form within N days (start with 5). Freshness is a scheduling property, not
just a per-puzzle one — three treemaps in a week would feel repetitive even if each puzzle
is individually good.

## Data trap found: entities that appear and disappear

**Ethiopia — today the world's 5th-largest coffee producer — is absent from the FAO series
before 1993**, because pre-split figures are filed under "Ethiopia PDR", a country that no
longer exists. An auto-generated 1990→2024 chart would have silently dropped it, producing a
chart that is wrong in a way no reader could detect.

The rank slope in the prototype excludes Ethiopia for exactly this reason.

**Required check before any dataset becomes a puzzle:** confirm that every entity to be drawn
exists across the entire period being charted, and drop the period or the entity if not.
Add this alongside the outlier check from doc 02 (the Central African Republic coffee figure).

## Accessibility notes from the build

- Treemap: colour restricted to **three ramp steps** so every block label wears the same ink
  and clears 5:1 contrast in both themes. Area already encodes magnitude, so colour only
  needs to separate blocks — measured with a contrast script rather than eyeballed.
- Dumbbell: the two dates are distinguished by **shape** (hollow ring = then, solid = now),
  not shade alone. Shade alone was too weak at dot size, especially in dark mode.
- Rank slope: line colour encodes **direction of travel** (risers, fallers, steady) — a real
  property of the data, not decoration.
- Multi-line: end labels are pushed apart with a minimum-gap pass and given leader lines
  where they had to move, so converging series stay readable.

1. Build a connected scatterplot puzzle — the funkiest form, not yet demonstrated
2. How the daily puzzle is chosen and locked to the date
3. Hosting, and what it costs
4. Whether a shareable result grid ships in v1

# Chart Game — daily runs, scoring, and hosting

_Last updated: 25 Aug 2026_

Fourth doc. See `01-data-sources-and-decisions.md`, `02-game-design.md`, `03-chart-forms.md`.

## Decisions settled this round (Tim, 25 Aug)

| Decision | Choice |
|---|---|
| Daily unit | **A run of 5 charts**, not one chart |
| Timing | **No timer** — points come only from hints spent |
| Hosting | **GitHub Pages**, with GitHub Actions for the weekly data refresh |
| New requirement | Shareable score, in the spirit of [MapTap](https://maptap.gg/) |

## Why a score changes the daily unit

Tim asked for a shareable score. With one chart and four options there are only four
possible outcomes, so nobody can meaningfully compare results — the score carries almost no
information. A run of five charts gives a real spread and makes comparison worth doing.

This is the difference between the Wordle model (one puzzle, share the *pattern*) and the
MapTap model (a run, share the *number*). Asking for a score picks the second.

## Scoring

| Outcome | Points |
|---|---|
| Named on first guess | 100 |
| After one hint | 60 |
| After two hints | 30 |
| Ran out of options | 0 |
| All five first-time | +100 bonus |

Maximum 600. No speed component — see below.

### Why no timer

A clock would push players to click fast and guess. The entire appeal of this game is
reading a chart carefully and reasoning from the evidence, so speed pressure works directly
against the thing that makes it good. Points come only from how few hints were needed, which
is already a measure of how well the chart was read.

### Share format

Plain text, so it pastes into WhatsApp, Discord or a group chat with no image, no login and
no tracking link:

```
Redacted Chart #128 · 420/500
🟩🟨🟩🟥🟩
🔥 4-day streak
https://…
```

🟩 first guess · 🟨 one hint · 🟧 two hints · 🟥 missed. The squares reveal the cost of each
chart and nothing about the answers.

## How the daily run gets picked — no server required

The entire game is a folder of static files. Nothing runs, nothing costs money, nothing can
go down. This works because the puzzle is not chosen by a server — it is derived in the
browser from the date.

```js
var LAUNCH = new Date(2026, 7, 25);
function startOfDay(d) {
  return new Date(d.getFullYear(), d.getMonth(), d.getDate()).getTime();
}
var runNo = Math.floor((startOfDay(new Date()) - startOfDay(LAUNCH)) / 86400000) + 1;
var run = RUNS[runNo];
```

### The build-time / run-time split

This is the core architectural idea:

- **Build time** (weekly, on GitHub's machines): fetch OWID data, pick forms, generate
  decoys, generate cryptic hints via an AI model, run the quality checks, write `runs.json`.
- **Run time** (the player's browser): read `runs.json`, work out today's run number, draw
  the charts, score the answers.

Nothing needs a live server, which is why hosting is free.

### Timezone

Uses the player's **own local date**, like Wordle. A new run arrives at your midnight rather
than someone else's. Consequence: Auckland is a run ahead of London for part of each day —
which is exactly why the share text names a run **number** rather than a date.

### Peeking ahead

Everything ships to the browser, so a determined player could read future runs out of the
JSON. Mitigation: the weekly build emits only the **next ~14 days**, so peeking gets two
weeks at most and the file stays small. Light obfuscation could be layered on top, but it is
a speed bump, not a lock — worth being honest about rather than pretending otherwise.

### Queue management

The build should fail loudly when fewer than 30 days of runs remain, so the game never
silently runs dry.

## Storage

`localStorage` holds today's progress, streak, best score and games played. Every read and
write must be wrapped in try/catch — it can be empty, stale, or throw outright in private
windows or where site data is blocked, and the game has to work correctly when it returns
nothing.

No accounts means no cross-device sync. Acceptable for v1.

## Hosting: GitHub Pages

Chosen for simplicity — one account covers the code, the scheduled refresh and the site.

**GitHub Pages limits** ([docs](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)):

- Free for public repositories
- Published site max **1 GB**; source repo recommended under 1 GB
- **100 GB/month** soft bandwidth limit
- 10 builds/hour soft limit — does not apply when deploying via a custom Actions workflow
- Custom domains and HTTPS supported
- **No commercial use** — no e-commerce, SaaS, or payment handling

The game is a few hundred KB, so size is irrelevant. Bandwidth is generous, though a genuine
viral day could brush the 100 GB soft cap; Cloudflare Pages is the fallback if that ever
happens (free tier: 500 builds/month, 20,000 files, 25 MiB/file, no stated bandwidth cap).

### ⚠️ The gotcha to design around

**GitHub automatically disables scheduled workflows in public repositories after 60 days of
no repository activity** ([docs](https://docs.github.com/actions/managing-workflow-runs/disabling-and-enabling-a-workflow)).
The weekly data refresh would silently stop after two months of Tim not touching the repo —
and commits made by the Actions bot are widely reported not to reset the clock.

Fixes, in order of preference:

1. A keepalive step in the workflow that pokes the repo through the API
2. Tim making any manual commit every couple of months
3. Moving the cron to Cloudflare Workers, which has no such rule

**Whichever is chosen, add a monitoring step**: the build should ping a dead-man's-switch
service, so a silent failure surfaces as an email rather than as stale puzzles nobody notices.

## The six steps

| # | Step | Why it's ordered here |
|---|---|---|
| 1 | Install an authenticator app | GitHub asks for it mid-signup; stopping halfway is the common frustration |
| 2 | Create the account (Free plan) | — |

## Decisions baked into the walkthrough

**Repository named `USERNAME.github.io`.** GitHub treats that exact name as a special case
and serves it at `https://username.github.io`, rather than the longer project-site form
`https://username.github.io/reponame`. Only one such site is allowed per account, which is
fine — this is the only project.

**Public repository.** Required for free GitHub Pages *and* for free unlimited Actions
minutes. Private repos need a paid plan for Pages and consume a 2,000-minute monthly budget
for Actions. Nothing sensitive goes in this repo, so public costs nothing.

**Web interface only, no local tooling.** Tim will use "Add file → Upload files" and the
in-browser editor. No Git client, no command line, no local install. This keeps the barrier
at roughly zero, and is entirely sufficient for a static site with a scheduled build.

## 2FA is now mandatory

GitHub requires two-factor authentication for accounts that take contributor actions —
creating repositories, publishing, running Actions — which describes exactly what Tim's
account will do
([docs](https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/about-mandatory-two-factor-authentication)).

Enrolment works as a notified 45-day window plus a 7-day grace period, after which the
account cannot access GitHub.com until 2FA is enabled. Community discussion through 2026 has
pointed at broader deadlines, with dates reported inconsistently across sources — so the
walkthrough deliberately avoids naming a specific date and simply treats 2FA as required
from the start.

Accepted methods: a TOTP app is the recommended primary; passkeys and security keys can only
act as backups, not as the primary method. SMS works in most countries but is discouraged.

# Mystery Chart — name, mobile, and onboarding

_Last updated: 26 Aug 2026_

Sixth doc. See docs 01–05.

## The game is called Mystery Chart

Tim's choice, 26 Aug. Replaces the working title "Redacted Chart". Applied everywhere:
the game, the share text (`Mystery Chart #128 · 420/500`), the holding page, and the
browser tab. The redaction motif — a black bar over the title that lifts when you solve
it — stays, because it's the mechanic, not the name.

Headline reworded from "Its labels are redacted" to **"Its title is blacked out"** — plainer,
and more accurate now that we've settled that only the *subject* is hidden while country
names and numbers stay visible.

## Working order agreed

Tim asked whether to refine here before setting up GitHub. Yes — the iteration loop here is
seconds, versus download-upload-wait through GitHub's web interface. Nothing built here is
wasted; the prototype becomes the real front end. GitHub setup is a fixed cost that doesn't
expire, and the artifact can already be shared with friends for playtesting.

Chosen priorities: **mobile first, then onboarding.** Difficulty calibration and hint-voice
work are parked for a later round.

## Mobile — the bug and the fix

**The problem:** every chart was drawn at a fixed 720-unit viewBox and scaled down by the
browser to fit. On a 390px phone that's 54% scale, so a 12.5px label rendered at ~6px.
Charts weren't broken, they were illegible — and it would have affected every puzzle we ever
made.

**The fix:** draw at the container's real pixel width, so one SVG unit is one CSS pixel and
a font-size of 12 renders as 12px on every device. Font sizes stop needing compensation
entirely.

```js
function metrics() {
  var w = document.getElementById("chart").clientWidth || 720;
  w = Math.max(300, Math.min(720, Math.round(w)));
  return { W: w, compact: w < 560 };
}
```

Margins and label counts still need explicit compact values — a 150px gutter is sensible on
a 720px chart and absurd on a 358px one:

| Form | Desktop | Compact (<560px) |

## Onboarding

1. **Intro** — the editorial headline, the pitch, four numbered rules, and a "Start today's

2. **Game** — a compact bar (wordmark, run number, chart counter, a `?` button) plus progress

3. **Results** — score, per-chart breakdown, share

vertical space on the game screen, which matters most on phones. The structure change solved

_Last updated: 26 Aug 2026_

## The fifteen puzzles

Three runs of five. Difficulty is mixed inside each run and no two neighbouring charts share
a form. Each puzzle carries a `diff` rating 1–5, revealed to the player only **after** they
answer — showing it first would anchor them and make their rating worthless.

| # | Subject | Form | Diff | Run |
|---|---|---|---|---|
| A | Cocoa production 2024 | Treemap | 2 | 3 |
| B | Coffee world ranking 1990→2024 | Rank slope | 3 | 1 |
| C | Fertility 1970→2023 | Dumbbell | 3 | 3 |
| D | Child mortality 1970–2024 | Multi-line | 4 | 3 |
| E | Alcohol per adult 2020 | Beeswarm | 2 | 2 |
| F | Population density 2023 | Lollipop (log) | 1 | 3 |
| G | Tourist arrivals 2024 | Lollipop | 1 | 1 |
| H | Wine production 2023 | Treemap | 2 | 1 |
| I | Internet use 2025 | Lollipop | 2 | 2 |
| J | GDP per capita 2025 | Lollipop | 3 | 2 |
| K | Banana production 2024 | Treemap | 4 | 1 |
| L | Obesity 2024 | Lollipop (with break) | 3 | 1 |
| M | Military spending 2025 | Diverging bar | 3 | 3 |
| N | Meat per person 2023 | Lollipop | 5 | 2 |
| O | Life expectancy 1950→2023 | Dumbbell | 2 | 2 |

## Why a deliberate spread, not ten more "medium" puzzles

Fifteen puzzles all pitched at one guess of "medium" would yield a single bit of feedback
("a bit hard"). A spread from 1 to 5, each with its intended rating and a per-puzzle rating
control, tells us **where Tim's line actually sits** — and whether our sense of difficulty
tracks his at all.

Instrumentation added:

- After each chart: "We pitched this one at N out of 5. How did it feel?" →
  Too easy / About right / Too hard
- On the results screen: **Copy difficulty notes**, producing a pasteable summary of every
  chart, its intended difficulty, the score, and Tim's verdict
- **Next run** replaces "play again", so all three runs are playable in one sitting

## What makes a puzzle hard

Emerging from building these, the difficulty dial has three independent settings:

1. **How iconic the top of the ranking is.** France/Italy/Spain is instantly wine. India/
   China/Indonesia/Brazil could be almost anything (bananas, diff 4).
2. **How close the decoys sit.** Obesity as a decoy for meat consumption is brutal — Tonga
   tops both. Mango as a decoy for banana is brutal for the same reason.
3. **Whether the answer needs a second inferential step.** Meat (diff 5) needs you to spot
   Mongolia's herding culture *and* India's vegetarianism; density (diff 1) needs only
   "these are all tiny places".

## Two new chart forms

- **Lollipop** (Ranking) — a lighter ordered bar; supports a **log scale** for ranges
  spanning orders of magnitude (density: 3.4 to 18,704) and an optional **break row** for
  showing highest and lowest with the middle omitted (obesity).
- **Diverging bar** (Deviation) — bars around an unlabelled reference line. Used for military
  spending against the 2% NATO line.

Form count is now seven. Lollipop dominates (6 of 15) because single-year cross-country data
genuinely *is* the Ranking family — that's the FT vocabulary being honest, not a lazy choice.

### Chart-craft fixes made while building

- **Nice axis ticks.** Dividing the max into five gave 14.46 / 28.92 / 43.38. Now snapped to
  1, 2, 2.5 or 5 × a power of ten, with the axis topping out on a tick.
- **Unit formatting.** "93,759,300" clipped out of the margin and "20000k" is nonsense. One
  unit is chosen per chart from its largest value, so every label is comparable: 94m, 72m, 58m.
- **Outlier clipping.** Ukraine at 39.6% of GDP is five times the next country; drawn at true
  length, every other bar collapsed to a sliver and the chart stopped reading as diverging at
  all. The bar is now clipped just past second place with a zigzag break, and the true value
  is still direct-labelled — the standard newspaper solution.

## Data traps found this round

Adding to the list in docs 02–04:

- **"Latest" can mean a projection.** `population-density` with `time=latest` returns **2100**
  — UN projections, not observations. Any auto-built puzzle must pin an explicit year or
  verify the year is not in the future.
- **`csvType=filtered` respects a chart's default country selection.** For charts with a
  preset selection it returns only those few countries, not all of them. Use
  `country=~ALL` to get everything. Silent, and easy to mistake for a small dataset.
- **Some slugs 500 rather than 404.** Several `share-electricity-*` slugs returned server
  errors repeatedly. The pipeline needs to treat a 500 as "skip this dataset and log it",
  not as a transient error worth retrying forever.

# Mystery Chart — what playtesting actually showed

_Last updated: 26 Aug 2026_

Eighth doc. Tim played runs 2 and 3 (ten puzzles) on 26 Aug and rated nine of them
"about right". **The ratings and the scores disagree, and the scores are the more useful
signal.**

## The data

| Puzzle | Pitched | Scored | Hints used |
|---|---|---|---|
| Tourist arrivals | 1/5 | 30 | 2 |
| Internet use | 2/5 | 30 | 2 |
| Bananas | 4/5 | 60 | 1 |
| GDP per capita | 3/5 | 60 | 1 |
| Meat per person | 5/5 | 60 | 1 |
| Wine | 2/5 | 100 | 0 |
| Obesity | 3/5 | 100 | 0 |
| Coffee rank slope | 3/5 | 100 | 0 |
| Life expectancy | 2/5 | 100 | 0 |
| Alcohol | 2/5 | 100 | 0 |

Run totals: **390/500 and 350/500.**

**Correlation between pitched difficulty and score: +0.04.** Our difficulty model predicted
nothing. Worse, it inverted: the two puzzles pitched *easiest* (1 and 2) produced the two
*worst* scores, while the two pitched hardest (4 and 5) both scored 60 — better than either.

Tim's "about right" is real and worth trusting — the game is fun and the scores land in a
good band. But it measures enjoyment, not difficulty, and it cannot be used to tune the
generator.

## Diagnosis: two different failures

**Tourist arrivals (pitched 1, scored 30).** The decoys were emigrants, domestic air
passengers, and university students. Ruling any of them out required *recalling* an
external fact (that the USA dominates domestic aviation, that Mexico leads emigration).
Nothing on the chart itself settled it. We assumed "Spain at number one" was an obvious tell;
it is only obvious to someone who already knows the tourism rankings.

**Internet use (pitched 2, scored 30).** A genuine fairness bug, not difficulty. The decoys
were bank accounts, city-dwelling and household electricity — and *all four options share
the same shape*: near-100% in the Gulf, very low in Burundi and Chad. Kuwait and Bahrain are
about 100% urban. This violated our own rule from doc 02 ("reject any decoy that is arguably
also true"). It was ambiguous, and Tim was right to need two hints.

## The rule this produces

Difficulty is not mainly about how iconic the ranking is. It is about **decoy separation**,
and the test is checkable:

> **Every decoy must be ruled out by something visible on the chart itself.**

Not by outside recall. Not by knowing a ranking already. By a number, a label, or a shape
that is on screen.

This is a far better rule than "decoys should be plausible" because a generator can verify
it. The three practical discriminators:

1. **Magnitude.** Spain's 94 million against a population of 48 million rules out anything
   counting residents — visible, decidable, no recall needed.
2. **The tail, not the head.** Burundi at 8.6% rules out literacy (~74% there) and running
   water (>60%). *The bottom of a chart is often the discriminating evidence, and we had
   been designing entirely around the top.*
3. **Ordering conflicts.** Côte d'Ivoire and Ghana leading rules out coffee, where they
   barely feature.

Corollary for difficulty rating: a puzzle's difficulty is roughly **how many inferential
steps separate the visible discriminator from the answer** — not how obscure the subject is.

## Repairs made

**Internet use** — decoys replaced with literacy, running water, and share of adults in paid
work. All three are now ruled out by the *bottom* of the chart (nothing has 100% of adults in
paid work; Burundi's literacy and water access are far above 8.6%). Hint 1 rewritten to point
at the tail rather than the Gulf. Re-pitched to 3/5.

**Tourist arrivals** — decoys replaced with emigrants, hotel and restaurant employment, and
domestic flights. The first two are now ruled out by magnitude alone: Spain's 94m exceeds its
own population. Hint order changed so the population comparison arrives second. Re-pitched
to 2/5.

## What this means for the automation

The generator needs a **discriminator check** before a puzzle ships: for each decoy, identify
the visible feature that rules it out. If no such feature exists, reject the decoy — it is
ambiguous, not hard. This joins the existing pre-flight checks:

1. Population-ranking test (doc 02)
2. Outlier sanity check (doc 02)
3. Entity-continuity check (doc 03)
4. Projection check — reject future-dated "latest" values (doc 07)
5. `country=~ALL` on filtered queries (doc 07)
6. **Discriminator check — new**

## The hint ladder is validated

Both mispitched puzzles were *rescued* by hints: Tim reached the right answer on both after
two hints, scoring 30 rather than 0. That is exactly the ladder's job — it converts an unfair
puzzle into a slow one instead of a dead end. Good evidence the hint design is sound before
we start generating them in bulk.

## Next

**Hints** — the agreed second priority. The hints written by hand now become the style guide
the automation copies, so the voice needs pinning down deliberately.

# Mystery Chart — hint style guide

_Last updated: 26 Aug 2026_

Ninth doc. **This is the specification the hint generator copies.** Tim chose the voice on
26 Aug after comparing four alternatives side by side.

## Voice: literary and oblique

Writerly, slightly withholding, treats the player as a grown-up. Not dry-factual, not matey,
not crossword-cryptic.

> "Two neighbours on the Gulf of Guinea between them fill nearly half this square."
>
> "The top three have been arguing about which of them does this best for roughly two
> thousand years."
>
> "The cliff at the far left is a war ending, not a policy working."

Characteristics to preserve:

- **A concrete image or a piece of history**, not a restatement of the data
- **Understatement.** The hint points; it does not explain
- **One sentence, occasionally two.** Never three
- **No jokes at anyone's expense**, and no winking at the player
- **British spelling and register**

Failure modes to avoid: purple prose, riddling for its own sake, and hints that are really
just the answer with a synonym swapped in.

## The ladder

Tim chose **atmosphere only** for the first rung. Each rung does a different job:

| Rung | Job | Eliminates |
|---|---|---|
| 1 | **Atmosphere.** A place, a period, or an oddity in the data. | Nothing |
| 2 | **The discriminator.** Points at the visible feature that kills a decoy (see doc 08). | At least one option |
| 3 | **Units and scale.** What is measured, and in what. | Narrows sharply |
| 4 | **The shove.** Near-explicit. | Should be unmissable |

## ⚠️ Only rungs 1 and 2 are currently reachable

With four options, the third wrong guess leaves one option standing and the answer is
revealed — so `hints[2]` and `hints[3]` **never display**. Sixty hints were written; thirty
can be seen.

Nothing is deleted: rungs 3 and 4 stay in the data as reserve. They become reachable in the
**UX phase** via an optional "show me a hint" button that costs points, letting a player buy
help without having to guess wrong first. That also gives players agency, which the current
design lacks entirely.

Until then, **rungs 1 and 2 carry the whole load** and must be written accordingly.

## The no-leak rule (mechanical, and enforced)

> **The first hint must contain no word from the answer's own semantic field.**

This is checkable by code, not judgement, which is exactly what the generator needs. The
check has two parts:

1. No significant word from the answer text itself (stopwords removed)
2. No word from the answer's semantic field — a small hand-built list per topic
   (`alcohol` → drink, law, prohibit, litre; `meat` → herder, livestock, cattle; and so on)

A script implementing this was run over all fifteen ladders. **Eight rungs failed.** Every
one has been rewritten.

### What the check caught

| Puzzle | The leak | Why it mattered |
|---|---|---|
| Alcohol | "what they share is a **law**" | "Law" + "zero" is prohibition, which is alcohol. Answer, rung 1. |
| Tourist arrivals | "its figure is mostly **religious**" | Pilgrimage → visitors → tourism. |
| Obesity | "imported **processed food**" | The answer wearing a coat. |
| Military spending | "one country is **spending** five times…" | The literal answer word. |
| Meat | "a country of **herders**" | Herders → livestock → meat. |
| GDP per capita | "**produce** far more than they consume" | Output is the answer. |
| Internet use | rung 1 was doing rung 2's elimination | Not a leak but a ladder-order error. |
| Population density | "a list of very **small places**" | Area → density. |
| Bananas | "it **exports** more of this" | Narrows to a traded commodity. |

Current state: **0 of 15 first hints leak.**

## Worked example — the repaired alcohol ladder

1. *"Four countries record exactly zero. Not nearly zero — zero."*
   Atmosphere. The oddity is stated without explaining it.
2. *"What those four have in common is a law rather than a shortage. The two highest are in
   the Balkans and the Caucasus."*
   The discriminator: no consumption measure has a legally-enforced floor of zero.
3. *"Measured in litres of the pure substance, per adult, per year."* (reserve)
4. *"Saudi Arabia, Kuwait, Mauritania and Somalia all sit at zero, for the same legal
   reason."* (reserve)

Note what moved: the word "law" was the strongest clue in the ladder and it was sitting on
rung 1. Demoting it to rung 2 is the whole fix.

## Generator requirements

1. Generate four rungs per puzzle in the voice above
2. Run the no-leak check on rung 1; regenerate on failure
3. Verify rung 2 names the visible discriminator identified by the decoy check (doc 08)
4. Rungs 3 and 4 can be templated from the OWID metadata — units and source come free
5. Queue for Tim's review in batches of ~50

Only rungs 1 and 2 truly need a model's judgement. That is roughly 730 hints a year, which is
a manageable review load and a small generation cost.

**UX** — the agreed third priority. Top of the list: the optional hint button, which unlocks
the two reserve rungs already written for every puzzle.

# Mystery Chart — UX pass and design simplification

_Last updated: 26 Aug 2026_

Tenth doc. Third and final item in the agreed order (difficulty → hints → UX).

## Six gaps found by audit

Rather than guess, the running game was instrumented and tested. All six were real.

| Gap | Severity | Fixed |
|---|---|---|
| **Tooltips were mouse-only** — no way to read any exact figure on a phone | Serious | Pointer events: mouse hovers, finger taps and the tooltip lingers 2.6s |
| **Mid-run reload lost everything** — back to chart 1 | Serious | Run checkpointed to `localStorage` after every action |
| Hint rungs 3 and 4 unreachable | Medium | "Give me a hint" button |
| No running score during play | Medium | Added to the game bar |
| No keyboard support | Low | 1–4 / A–D select, H buys a hint, Enter advances |
| Hints had no `aria-live` | Low | `aria-live="polite"` |
| Help button read "Start today's run" mid-run | Low | Now reads "Back to the chart" |

**The touch bug was the worst of these.** The exact numbers *are* the evidence the game runs
on, and they were unreachable on the platform most people will play on. Worth remembering as
a general lesson: a hover interaction is not an interaction on a phone.

## The hint button, and why it costs what it costs

Score is now keyed on **how many rungs have been revealed**, regardless of whether a wrong
guess or a purchase revealed them. Buying help costs exactly what guessing wrong costs.

| Rungs revealed | Points |
|---|---|
| 0 | 100 |
| 1 | 60 |
| 2 | 30 |
| 3+ | 15 |
| Ran out of options | 0 |

This unlocks the two rungs already written for every puzzle, and gives players agency they
previously had none of — you can now choose to spend points rather than only lose them.
Solving after buying every hint scores 15, which is better than 0 and keeps a stuck player
learning rather than failing. The button disappears once a chart is solved rather than
lingering greyed-out.

Result-share marks extended: 🟩 first guess · 🟨 one hint · 🟧 two hints · 🟦 three or more ·
🟥 missed.

## Run persistence

Saved after every meaningful action and restored **only if the saved run is today's or
later**. On a new day `runNo` increases past anything stored, so yesterday's half-finished
game is correctly abandoned rather than resumed — while the prototype's "Next run" button,
which deliberately jumps ahead of the date, still survives a reload.

Both branches are covered by tests: a planted stale run is ignored; a current run restores
its struck-out options and revealed hints exactly.

## Design: simpler, after Chartle

Tim (26 Aug): *"I really like how simple Chartle is... I want it a bit more elaborate than
that, as Chartle doesn't do hints or text and it's a bit boring, but the simplicity in the
design speaks to me."*

**The diagnosis:** the page was elaborate partly because it was carrying *our* scaffolding in
the player's view. Every puzzle was topped and tailed with `EXHIBIT G`, `SUBJECT WITHHELD`,
`FT VISUAL VOCABULARY · RANKING`, `LOLLIPOP · 2024` — four meta-labels that mean something to
us and nothing whatsoever to someone trying to read a chart.

**The principle applied:** *nothing appears during the puzzle except the chart, the question
and the options. All meta-information moves into the reveal*, where it stops being noise and
becomes interesting.

Removed from the playing view:

- The exhibit / subject-withheld row
- The FT Visual Vocabulary footer
- The entire "Under the hood" design-notes section (it lives in docs 01–09 now)
- The panel's drop shadow

Kept, because it is the identity rather than the chrome: the black redaction bar that lifts
on solving.

Added: **one quiet line** under the chart giving the period (`2024`, `1990 → 2024`). Every
puzzle now carries an explicit `period` field. This is the single piece of meta a player
genuinely needs, and dropping it would have been bad data practice rather than simplicity.

Moved into the outcome panel: the chart form and FT family (`Lollipop · Ranking`), alongside
the source credit.

The chart now occupies the space four labels used to.

## Calibration instrumentation removed (Tim, 26 Aug)

The per-chart difficulty chips ("Too easy / About right / Too hard"), the "We pitched this at
N out of 5" line, and the "Copy difficulty notes" button have all been **deleted**. They were
scaffolding for the calibration round in doc 08 and had served their purpose; leaving them in
would have contradicted the simplicity rule the same day it was set.

The `diff` field is **retained in the puzzle data**. It carries no UI now, but it is the
training signal the generator will need when it starts rating its own output — and the
findings it produced are preserved in doc 08.

Results screen is now just: score, per-chart breakdown, Copy result, Next run.

## Rule going forward

> The playing view holds the chart, the question and the options. Nothing else earns a place
> there. Anything we want to know goes in the reveal.

| Ink | `#1A1A1B` | `#FFFFFF` |

|---|---|---|

### How the colours were chosen

Not by eye. Hand-picked "punchy" hexes failed the accessibility validator twice, so the
colours were **generated**: a script converts OKLCH to sRGB, binary-searches the maximum
in-gamut chroma at a given lightness and hue, then scans the permitted lightness band to find
the most saturated colour that still clears the contrast floor. Script at `/home/claude/oklch.py`
in the working session; worth rebuilding if this is ever revisited.

Two findings from that process:

1. **Forcing one lightness across all hues does not work.** Yellow at mid-lightness is olive.
   Each hue has its own lightness at which it is punchiest within the band.
2. **Yellow had to be dropped entirely.** The best in-band yellow (`#a89500`) sat too close
   to green: normal-vision ΔE 14.2, below the floor of 15. Replaced with violet, after which
   both modes pass every check with worst adjacent ΔE 9.5 (CVD) and 26.5 (normal vision).

### One design change that followed

The lollipop dots used the three-step blue ramp. An ordered list already encodes magnitude by
position, so shading it as well just muted the marks. Now a single strong blue.

## 2. No em-dashes

Tim: *"I don't want to see any m-dashes in the hints, answers or trivia."*

Removed from every player-facing string: 10 in hints, 8 in the explanation text, plus the
intro copy. Each was rewritten rather than character-swapped, so the sentences still read
properly (a comma, a full stop, or a colon depending on what the clause was doing).

En-dashes in numeric ranges (`1970–2024`) are kept: they are notation, not prose.

**House style, applying to generated hints too:** no em-dashes in any text a player sees.
This joins the no-leak rule in doc 09 as a check the hint generator must satisfy.

## Also fixed

- Multi-line x-axis showed `2020` and `2024` overlapping. Tick list reduced to
  1970/1980/1990/2000/2010/2024.
- Phone header wrapped onto two lines with the new score readout. Wordmark and meta sized
  down under 560px; now 38px, a single line.

Palette validated in both modes: lightness band, chroma floor, CVD separation, normal-vision
floor and surface contrast all pass. Full regression re-run: hint purchase scoring, run

No console errors.

# Mystery Chart — typography

_Last updated: 26 Aug 2026_

Twelfth doc. Tim asked to change the font to **GT America** (26 Aug).

## GT America cannot be used yet, and why

GT America is a commercial typeface from [Grilli Type](https://www.grillitype.com/typeface/gt-america).
It is not on Google Fonts and cannot be linked from a CDN.

From Grilli Type's own [licensing information](https://www.grillitype.com/information):

- **Self-hosting is the only option.** They do not run a font CDN; you buy the files and put
  them on your own site.
- **Web pricing is tiered by projected unique monthly visitors**, and the licence must cover
  the combined traffic of all sites using it.
- **Trial fonts exist but are explicitly not for this.** They carry a minimal character set,
  lack OpenType features, and are licensed for mockups and client presentations. Using them
  on a live public game would breach the licence.

So GT America needs a purchased webfont licence before it can go anywhere near the site. That
is Tim's call, not a technical blocker we can engineer around.

**If Tim buys it**, the swap is small: replace the Google Fonts `<link>` with `@font-face`
rules pointing at the licensed `.woff2` files, and change one variable. Roughly ten minutes.
Note that a published Artifact blocks external font hosts (Google Fonts excepted), so in the
prototype the files would have to be inlined as base64 data URIs; on the real GitHub Pages
site they can simply sit in the repo.

## What was done instead: Archivo

[Archivo](https://fonts.google.com/specimen/Archivo) (Omnibus-Type) is the closest free
match. GT America's conceit is a bridge between European grotesques (Akzidenz, Helvetica) and
American gothics (Franklin, News Gothic); Archivo comes from the same grotesque lineage and,
usefully, carries a **width axis** as GT America does, so the family has somewhere to go if
the design ever wants a condensed or extended cut.

Loaded as a variable font across width 75–125 and weight 400–700.

## One family, not three

The page previously ran Newsreader (serif display), IBM Plex Sans (body) and IBM Plex Mono
(labels and figures). All three are gone.

A single grotesque is the more consistent answer to the Wordle-simplicity direction from
doc 11, and it is what GT America would have done anyway. Compensating changes, since a
grotesque carries less character than a serif at display sizes:

- Headline, wordmark, verdict and score: weight raised to 600–700, tracking tightened to
  −0.02 to −0.045em
- Hint text: the italic serif became upright. Italic grotesque at that size reads as an
  error rather than a voice; the accent rule and wash carry the emphasis instead
- **Figures: `font-variant-numeric: tabular-nums`** on the body and on every SVG. Losing the
  monospace face would otherwise have broken the alignment of every axis tick, value label

stack *inside* a single-quoted JavaScript string, producing `''Archivo', ...'` and a syntax
error that stopped all rendering. Caught by the boot diagnostic, not by eye.

looking at screenshots. A blank page and a subtly-wrong page look identical in a diff.

# Mystery Chart — analytics

_26 Aug 2026_

Tim asked how to see how many people are playing and what they score. Chose **visitors and
scores**, not a leaderboard.

## Starting position

Nothing was recorded anywhere. The game is a static file with no server; every score lives in
`localStorage` on the player's own device and is never transmitted. GitHub Pages exposes no
visitor logs. Also worth noting to Tim: **none of this can be backfilled**, so it needed
adding before the link is shared widely.

## Tool: GoatCounter

Chosen over the alternatives because it is free for personal use, **cookieless**, and has a
documented events API. One script tag plus a `count()` call.

**Why cookieless is not a detail:** cookie-based analytics (Google Analytics) requires a
consent banner under UK rules. On a game people play for ninety seconds with their coffee,
a banner is the first thing they would see and would cost real players. Cookieless tools
store nothing on the device and avoid the banner entirely.

Rejected: Google Analytics (cookies, banner, heavy); Cloudflare Web Analytics (pageviews only,
weak on custom events); Umami Cloud (proper event properties, but the free-tier limits could
not be confirmed at time of writing — worth revisiting if event volume grows).

**GoatCounter limitation:** events are named paths and carry no numeric properties, so scores
are recorded as bucketed event names rather than as numbers to be averaged. Adequate for a
distribution; noted in case a future need for real numeric aggregation forces a move.

## What is tracked

| Event | Meaning |
|---|---|
| _(pageview)_ | Visitors, referrers, countries, device type |
| `play/start` | A run was begun |
| `play/complete` | A run was finished (start vs complete = drop-off rate) |
| `score/300s` | Score band, in hundreds; `600` for a perfect run |
| `chart/<slug>/<tier>` | Per-puzzle outcome: `first`, `hint1`, `hint2`, `hint3`, `missed` |

No cookies, no identifiers, nothing about who anyone is. A line in the results screen says so
plainly: *"No cookies, no accounts, no sign-in. Anonymous counts only."*

## The per-chart event replaces manual difficulty calibration

This is the significant one. Doc 08 recorded that our own difficulty ratings correlated with
Tim's actual performance at **+0.04** — pure noise — and that the fix was a laborious manual
rating round.

`chart/<slug>/<tier>` gives the same signal from every real player, continuously. The share
of players solving a puzzle first-time *is* its difficulty, measured rather than guessed. Once
enough runs have accumulated this becomes the training signal for the generator, and the
manual calibration loop can be retired for good.

## Implementation notes

- The loader is **inert until Tim pastes his own code**: the placeholder
  `https://YOURCODE.goatcounter.com/count` simply fails to resolve, and the game is
  unaffected. This means the same file works before and after signup.
- `track()` is wrapped in try/catch and checks that `window.goatcounter` exists. An
  ad-blocker, an offline player or an unset code must never break play. A meaningful share of
  visitors will block the script; the counts are therefore a **floor, not a census**.
- Script loaded over explicit `https://` rather than the protocol-relative `//` form that
  GoatCounter's docs show. The legacy form resolves to `file://gc.zgo.at/...` when testing
  locally and throws `ERR_INVALID_URL`. Caught by the regression run.

## Score faking

Flagged to Tim: any score sent from a browser can be forged. Irrelevant for aggregate
curiosity, fatal for a competitive leaderboard. This is the main reason a leaderboard is a
much larger job than it appears, and it stays out of scope.

3. Upload and commit
4. Dashboard at `https://<code>.goatcounter.com`

# Mystery Chart — the difficulty ramp

_26 Aug 2026_

Tim asked for the run to get harder as it goes: 4 options on chart 1, rising to 8 on chart 5,
with multipliers to match.

## What changed

| Chart | Options | Multiplier | Perfect |
|---|---|---|---|
| 1 | 4 | ×1 | 100 |
| 2 | 5 | ×1.5 | 150 |
| 3 | 6 | ×2 | 200 |
| 4 | 7 | ×2.5 | 250 |
| 5 | 8 | ×3 | 300 |

Run total **1,000**, plus a **200** perfect-run bonus. The multipliers were chosen so the
maximum lands on a round 1,000 and the last chart is worth triple the first, which is roughly
proportionate to the change in guess odds (1-in-4 to 1-in-8).

## Scoring rebuilt around cost, not hints

Previously the tier came from hints revealed. That broke with eight options: a player could
guess wrong five times, exhaust the four hints, and still be scored as if they had only spent
four. Now a single `cost` counter increments on **either** a wrong guess or a bought hint, and:

```
POINTS = [100, 60, 30, 15, 5, 0, 0, 0]   // indexed by cost
points  = POINTS[cost] × multiplier
```

The ladder reaching zero matters. With eight options the answer can always be found by
elimination, so brute force had to stop paying. Verified: solving chart 5 after six wrong
guesses scores 0.

## Sixty new decoys

Every puzzle now carries **one answer and seven decoys**, so any puzzle can appear at any
position. The data model changed from `options: [...] + answer: <index>` to
`answer: "<text>" + decoys: [...]`, which is also the shape the generator should emit.

All new decoys were written against the discriminator rule from doc 08: each must be ruled out
by something visible on the chart. The internet-use puzzle was the constrained one, since bank
accounts, electricity and city-dwelling all share its Gulf-100/Burundi-9 shape and remain
genuinely ambiguous; its new decoys (share under 30, measles vaccination, journeys by car,
home ownership) are all killed by the top or the bottom of the chart.

## Deterministic shuffle

Options are shuffled with a seed derived from the run number and position, so every player
sees the same options in the same order on the same day, with no server to agree it.

## Runs reordered

Run 3 was `[8, 14, 9, 4, 13]` — difficulties 3, 2, 3, 2, 5. Now `[14, 4, 8, 9, 13]` — 2, 2, 3,
3, 5. All three runs now climb in intrinsic difficulty so that ramp reinforces the option ramp
rather than cutting across it.

## Three bugs the tests caught

1. **The redaction bar leaked the next answer.** Advancing to the next chart let the bar
   animate back in over 620ms, during which the incoming title was readable. Fixed by snapping
   the bar back with the transition suppressed and a forced reflow. Found by screenshotting
   mid-transition on a phone, not by reasoning.
2. **`H` collided with the hint shortcut.** Extending the option letters to A–H meant pressing
   H selected option H instead of buying a hint. Hint shortcut moved to `?`.
3. **The banana treemap was 52% "Rest of world".** With the aggregate block dominating, the
   evidence the puzzle depends on (Ecuador 4th, Angola 8th) was unlabelled and unreadable.
   Now drawn as the twelve largest growers, where India reads 37% and both clues are legible.
   Hint 3 reworded from "nearly a fifth of the world's supply" to "more than the next three
   put together", which is true of the chart as drawn.

## Copy updated

Rules now read "Score out of 1,000", explain that the first chart offers four options and the
last eight, and note that a hint costs the same whether you guess wrong or ask outright.

Share marks extended: 🟩 first · 🟨 one · 🟧 two · 🟦 three · ⬜ four or more · 🟥 missed.

## Verified

Ramp (4→8 options, ×1→×3), points at every tier, perfect run = 1,200, brute force = 0, run
persistence, stale-run rejection, keyboard A–H and `?`, eight options on a 390px phone with no
overflow, both themes. No console errors.

Intro rules rewritten too: the second rule is now headed "It gets harder as you go" and the
fourth "The harder charts are worth more", rather than burying both in a sentence about scoring.

## 2. "Run #4 complete" — a bug that would have shipped

Tim asked what the run number referred to. Two separate problems:

**The launch date was hardcoded to a date already in the past** (25 Aug 2026). The run number is
days-since-launch, so whenever Tim actually went live his first players would have opened the
game on "Run #47" or similar. Meaningless, and it breaks the shared-identity purpose the number

Now a labelled settings block at the top of the script, next to where the analytics code goes:

```js
/* ==================== SETTINGS ====================
   Set this to the day you actually go live. Everyone playing on that date sees
   "Run #1", and the number climbs by one a day from there.                  */
var LAUNCH = new Date(2026, 8, 1);      // 1 September 2026
```

Clamped with `Math.max(1, ...)` so a future launch date still reads Run #1 rather than a
negative number.

**The prototype's "Next run" button incremented the shared run number.** That is what produced
"Run #4". Extra runs are now explicitly **practice**: the button reads "Play a practice run",
the game bar shows "Practice" instead of a run number, the results heading says "practice run
complete", and the share text says "Mystery Chart practice" rather than claiming a run number
that means nothing to the recipient. Streaks only count the real daily run.

**Follow-on bug found:** a practice run was checkpointing itself to `localStorage`, overwriting a
half-finished daily run. `saveProgress()` now returns early during practice.

## 3. Hints moved above the options

Tim's worry was that a hint appearing below eight options would be missed on a phone. Correct.
Hints now appear directly under the chart and above the question's options, which is also the
more logical reading order: chart, evidence, hint, answer.

Added: when a hint arrives, if it is not fully in the viewport the page scrolls it into view
(centred, and instant rather than smooth under `prefers-reduced-motion`). The measurement is
deferred by one `requestAnimationFrame`, because inserting the hint pushes the options down and
measuring immediately reads the pre-reflow layout.

## ⚠️ The bug this uncovered: hints were free

Chasing why the scroll never fired revealed the real cause:

```js
$("hintbtn").addEventListener("click", showHint);   // wrong
```

`addEventListener` passes the click event as the first argument, and `showHint`'s first
parameter is `alreadyCharged`. A truthy event object therefore meant **every hint bought with
the button skipped `cost++` entirely**. Buying three hints and answering correctly scored the
full 100 instead of 15.

Introduced with the difficulty ramp and live ever since. Fixed by wrapping the handler:
`function () { showHint(); }`.

**Why the tests missed it:** the hint-purchase scoring test was written before `alreadyCharged`
existed and never re-run after the ramp changed the scoring model. The keyboard shortcut called
`showHint()` correctly, so that path always worked. Lesson: when a function gains a parameter,
re-check every call site, especially ones passed directly as callbacks.

but not for a public one. Twenty-one more puzzles would take it to four weeks,
which is roughly where a daily game stops feeling thin.

# Data sources beyond OWID: what was tested and what works

Tested 27 August 2026. Every verdict below comes from a live request made in
that session, not from recollection. A refusal records what this environment
could reach that day, not necessarily what the source refuses in general.

Full write-up: https://claude.ai/code/artifact/b15e7310-671b-44ce-8240-7f2fb4c3b784

## Verdicts

| Source | Access | Verdict |
|---|---|---|
| Our World in Data | CSV per chart, no key | Keep as primary backbone |
| World Bank | JSON, no key, 70 databases | Adopt as second backbone |
| WHO GHO | OData, no key, **searchable catalogue** | Adopt as the discovery tool |
| Eurostat | JSON-stat, no key | Adopt, but EU-only coverage |
| OECD | SDMX, no key, dimension-index encoded | Third tier, needs a decoder |
| FAOSTAT | 401 on two endpoints | Reach it through OWID instead |
| Wikidata SPARQL | domain blocked by the sandbox | Parked, untested rather than rejected |

## Working request patterns

```
api.worldbank.org/v2/country/all/indicator/SH.ALC.PCAP.LI?format=json&date=2019
ghoapi.azureedge.net/api/Indicator?$filter=contains(IndicatorName,'suicide')
ghoapi.azureedge.net/api/{IndicatorCode}
ec.europa.eu/eurostat/api/dissemination/statistics/1.0/data/{code}?format=JSON
sdmx.oecd.org/public/rest/dataflow/{agency}?format=jsondata
sdmx.oecd.org/public/rest/data/{agency},{dataflow},1.0/all?format=jsondata
```

Notes from testing:

- World Bank returns regional aggregates mixed in with countries. Filter them out.
- WHO's `$filter=contains(IndicatorName,'x')` is the single most useful thing
  found. It turns subject discovery from guessing into a query. Searching "road"
  returned 28 indicators; "suicide" returned 5; "sex" returned 25.
- Eurostat `ilc_scp09` is "persons getting together with family or friends by
  sex, age, educational attainment and frequency", 1,050 observations. That is
  the register the funnier puzzles need.
- OECD `format=csvfilewithlabels` comes back as binary that the fetch tool
  cannot read. Use `format=jsondata` and resolve the dimension indices.
- Everything runs through WebFetch. There is no unattended shell here that can
  hit these hosts, and blocked fetches must not be routed around. So the weekly
  pipeline is a scheduled Claude session, not a cron script.

## Recommended architecture changes

Three, in order, before any automation is wired up:

1. **Puzzles move out of `index.html`** into a separate data file. Regenerating
   a 149KB file that also holds every chart renderer is how the sparse-array bug
   reached day 5 last time.
2. **Replace the hand-dealt `RUNS` array with a scheduler.** Pick five puzzles
   for date D from a pool, seeded by the date, respecting the difficulty ramp,
   no adjacent repeated forms, and nothing used in the last 90 days. Adding a
   puzzle then extends the runway without re-dealing. This is what makes running
   for years possible.
3. **The pre-flight checks become one script.** Seven decoys, four hints, no em
   dash, no answer word in hint one, treemaps sorted and summing to their total,
   beeswarm labels present in the data, ascending difficulty, no adjacent
   repeated forms, plus the Playwright sweep.

## The pipeline

Two loops at different cadences sharing one candidate bank.

- **Monthly trawl** — search the catalogues, rate candidates against the
  discriminator rule, top the bank up to about 120.
- **Weekly build** — draw 35 from the bank, fetch, draft, check, ship a file
  plus a report naming the runway and flagging only the puzzles the checks could
  not vouch for (roughly six to eight for human review).
- **Feedback** — the `chart/<slug>/<tier>` analytics events say what players got
  wrong and what they paid hints for. That steers the next trawl.

Build the bank before building the machine. The first trawl sets the standard
for every automatic one after it.

## The funny brief

One cheeky puzzle per run, placed second or third. Seven a week, about a fifth
of the pool.

What makes one land: a mundane subject, an unexpected leader, a reveal that
works as a punchline, and hints written exactly as straight as the ones about
child mortality. The deadpan is the joke.

Where the material actually is: FAO food balance sheets via OWID (ice cream,
cheese, offal), WHO alcohol by beverage type and road deaths attributed to
alcohol, OECD time use, Eurostat social participation and material deprivation,
World Bank Findex, UNODC crime categories.

Two limits. Punch at the comfortable, never at a poor country's hunger figures.
And the series must be one somebody actually maintains: one made-up number
discredits every other chart in the game.

**On "bed partners per capita"** — the right register, but no honest source
exists. Every ranking in circulation traces to commercial surveys rather than
statistical agencies, and none agree with each other. WHO's catalogue in that
area covers sexual violence, sex work and syphilis prevalence, which is real and
important and entirely wrong for a game with a wink in it. The nearest honest
neighbours are age at first marriage, divorce rates, and the share of young
adults still living with their parents.

# The dealer, and splitting the source

27 August 2026. The change that makes running for years possible.

## What was wrong

Two things, and they were the same thing.

The runs were written out by hand: a `RUNS` array of index lists that I searched
for with a randomised solver in Python and pasted into the file. Adding puzzles
meant re-dealing the whole deck. Splicing a new batch meant editing a 190KB file
that also held every renderer.

Both bugs that reached Tim came from that. A generator emitted a stray comma and
left a hole in a series array, and the chart silently failed to render on one day
out of eight. A new slope puzzle went in without `leftYear`/`rightYear` and its
column headers read "undefined" twice.

## The dealer

`RUNS` is gone. `dealRun(n)` computes the five puzzles for run `n`.

```
runsPerCycle = floor(pool / 5)
cycle        = floor((n - 1) / runsPerCycle)
index        = (n - 1) % runsPerCycle
```

`dealCycle(cycle)` seeded-shuffles the whole pool with `(cycle + 1) * 2654435761`,
cuts it into runs of five, sorts each run by difficulty, then runs a bounded
deterministic repair pass: walk every pair of puzzles sitting in two different
runs and swap whenever it lowers the combined cost.

`runCost` weights what we mind: two of the same form back to back (6), a rare
form doubled (4 each — slope, diverging bar, multi-line), a form appearing three
times (3 each), opening above difficulty 2 (2), closing below difficulty 4 (2).

**Guaranteed by construction:** the same five for everyone on a date, no puzzle
twice inside a cycle, difficulty rising across the run. **Best effort:** form
variety. If the repair pass cannot reach a clean deal the run still plays.

Results against the current pool of 50: 400 consecutive runs all deal at cost
zero, no adjacent form repeats anywhere in 1,600 neighbour pairs, every run opens
at difficulty 2 or less and closes at 4 or more. Forty fresh cycles deal in 69ms,
so a page load pays under 2ms.

Tested at pool sizes 3, 5, 7, 12, 47 and 50: no throws, every run playable, a
pool below five degrades to one short run rather than breaking. With 47 puzzles
the two that rest each cycle rotate, because the shuffle differs per cycle.

Two independent browser contexts at different window sizes on the same simulated
date were checked on days 1, 4, 12 and 31: identical five each time.

**Adding a puzzle now extends the runway on its own.** No re-dealing, ever.

## The source split

```
src/engine.html   renderers, dealer, scoring, chrome   79 KB
src/puzzles.js    the pool, and nothing else          111 KB
build.py          assembles both outputs
```

`build.py` substitutes the data into `/* @@PUZZLE-DATA@@ */`, writes the fragment
to `redacted-chart.html` (what the test scripts read) and the wrapped single file
to `site/index.html` (what gets uploaded). Verified byte-identical to the
pre-split file on the first build.

Tim still uploads **one** file. The split is upstream of the build, so it costs
him nothing and it means a new batch can no longer reach renderer code.

It also retires the head-wrapper block that had been retyped by hand a dozen
times this session — that lived nowhere and was re-derived every build.

## Tooling now

| Command | What it does |
|---|---|
| `python3 build.py` | assembles both outputs from `src/` |
| `node preflight.mjs` | 15 content checks plus three cycles of the dealer; exit 1 blocks the ship |

3. **A wrong answer buys a hint** — Hints start cryptic and end obvious. Ask for one early if you like; it costs the same.
4. **The harder charts are worth more** — Naming the last chart first time is worth triple the first, and a clean sweep pays a bonus on top. There's no clock.

## Deployment gotchas hit along the way

- **`index.html` must be at the repo root.** It went missing once and Pages fell back
  to rendering `README.md`.
- **A card image must be a real file at a real URL.** `og:image` is fetched by a
  crawler on Facebook's or Slack's servers, not rendered by a browser: data URIs and
  anything embedded in the HTML are invisible to it. Tags pointing at a 404 preview
  worse than no tags, because `summary_large_image` renders an empty box.
- **Filenames are exact.** The card was uploaded as `socialcard.png` while the tags
  named `social-card.png`. One hyphen, total failure, no error anywhere.
- **Post the `https://` URL when testing.** A bare domain becomes `http://`, which
  redirects, and Slack's unfurler is inconsistent about following redirects.
- Facebook's "This URL hasn't been shared on Facebook before" is not an error. It
  means nothing is cached yet; click **Fetch new information**.

# The catalogue, the fetch blocker, and where the sources actually stand

31 August 2026. Tim asked for 50 new puzzles (ten more days) plus a spreadsheet of
everything in the pool, and asked to be told if we are running out of sources.

The spreadsheet exists. The 50 puzzles do not, for a reason worth recording.

## The fetch blocker

**`web_fetch` strips query parameters.** Tested twice, both times conclusive:

| Requested | What came back |
|---|---|
| `per-capita-milk-consumption.csv?csvType=filtered&country=~ALL&time=2022` | Resolved to `csvType=full`. Every country, 1961 to 2023, truncated mid-alphabet at Fiji. |
| `api.worldbank.org/.../SP.POP.TOTL?format=json&per_page=300&date=2024` | All three parameters dropped. XML, 50 rows per page, page 1 of 350, first entity an aggregate. |

Every working request pattern in doc 21 is query-string based: OWID's `time=` and
`country=~ALL`, World Bank's `date=` and `per_page=`, WHO's `$filter=contains(...)`,
Eurostat's JSON-stat dimension calls. None of them survive the tool.

There was a second, quieter constraint: `web_fetch` will only take a URL that already
appeared in a search result, and editing the *path* (swapping one World Bank indicator
code for another) is rejected. So every dataset costs a search before it costs a fetch.

**The fix, applied 31 Aug:** Tim added `ourworldindata.org`, `api.worldbank.org`,
`ghoapi.azureedge.net`, `ec.europa.eu`, `sdmx.oecd.org` and
`*.frame.claudeusercontent.com` to the sandbox allowlist at
claude.ai/settings/capabilities → Code execution and file creation → Allow network egress
→ package managers and specific domains. That last domain also closes the doc 22
review-page loop, where a session could publish a review page but never read the notes back.

Bash `curl` keeps parameters. Verify all six before building anything: a 403 carries an
`x-deny-reason` header, and there are open reports of named domains silently not applying.

## The pool can be read straight off the live site

`raw.githubusercontent.com/timgouds/mysterychart/main/index.html` is reachable from bash
and holds the deployed game. The pool extracts cleanly:

```
sed -n '687,2196p' live.html > pool.js      # line 687 is ALCOHOL, which PUZZLES references
echo 'console.log(JSON.stringify(PUZZLES));' >> pool.js
```

Line numbers will drift; find them with `grep -n "var PUZZLES" live.html`. This is a better

## The catalogue

`mystery-chart-catalogue.xlsx`, four tabs: every puzzle with its answer, all seven decoys,
all four hints, form, difficulty, source, slug and the `why`; a schedule of runs 1 to 20;
source and form coverage; and a read-me.

The dealer was reimplemented in `dealer.mjs` / `deal.mjs` to generate the schedule, and
checked against the live game: cost zero on all ten runs, and 31 August lands on Run #6.

**The schedule is derived, not fixed.** `dealRun(n)` is a function of the whole pool, so
adding one puzzle re-deals every future run. The Schedule tab is correct for a pool of 50
and wrong the moment puzzle 51 lands. Nothing breaks; the dates move. Regenerate it after
every batch.

Note also that cycle 2 (runs 11 to 20) is a fresh shuffle seeded on the cycle number, not a
replay of cycle 1. A player still meets all 50 within 20 days. That is the real runway.

## Are we running out of sources? Not sources. OWID.

The binding constraint is not catalogue size. It is the rule from doc 03, that visible
labels must be entities and the hidden thing must be the measure, plus the discriminator
rule from doc 08. Between them a large indicator library yields few legal puzzles.

Within that, the mix is badly lopsided:

| Source | Puzzles | Read |
|---|---|---|
| Our World in Data | 36 (72%) | Headline cross-country rankings largely spent |
| World Bank | 12 (24%) | Barely scratched, ~1,500 indicators |
| Eurostat | 1 (2%) | Effectively untouched |
| WHO GHO | 1 (2%) | Effectively untouched |
| OECD | 0 | Never used at all |

Doc 21 identified Eurostat, WHO and OECD as viable and then never exploited them. Between
them they account for two of fifty. **The next 50 should invert the mix:** majority
non-OWID, with OWID used only where it is genuinely the best source rather than the most
convenient. WHO's `$filter=contains(IndicatorName,'x')` search is the discovery tool that
turns subject-finding from guesswork into a query, and it has never actually been used to
build a puzzle.

Two further gaps the coverage tab makes visible:

- **Lollipop is still 14 of 50 (28%)**, and only 17 of 50 puzzles use time. Doc 16
  recommended making change over time the default and requiring a snapshot to justify
  itself. That has not happened.
- **The funny brief from doc 21 has produced nothing.** One cheeky puzzle per run, placed
  second or third, deadpan hints. Zero of the current 50 read that way.

If four sources ever genuinely run dry, the ones to test are UNODC, UNESCO UIS, IEA, ITU
and IPU. Untested as of this session; a list to try, not a verdict.

## The dealer now knows what has already been broadcast

Tim objected to the amount of recycling in the schedule. Simulating it confirmed the
objection and showed the cause was not pool size. With 50 new puzzles added, the old
dealer would still have put an already-seen chart in **17 of the next 19 runs**, and run 9
would have been four repeats out of five.

`dealCycle` shuffled the whole pool each cycle. That guarantees no repeat *within* a cycle
and nothing at all across cycles, which is a much weaker promise than it sounds once the
cycle is 20 days long. Doubling the pool doubles the cycle and does nothing to stop next
month pulling from week one.

**Replaced with a forward dealer.** It runs from run 1 keeping a last-seen record, and
each run takes `NEW_PER_RUN` (4) charts nobody has seen plus 1 from those unseen longest.
When the unseen queue empties it degrades to a pure longest-unseen rotation rather than
breaking, which is the cooldown scheduler doc 21 recommended and nobody built.

- `HISTORY_SLUGS` freezes runs 1 to 6 to what actually aired, **keyed on slug, not index**.
  An index-keyed record corrupts silently the moment the pool is reordered; an unresolvable
  slug warns in the console and is dropped.
- Form variety is preserved by trying 240 seeded draws per run and keeping the lowest
  `runCost`. 39 of 40 runs deal at cost zero, matching the old repair pass.
- `MAX_RUN` of 3650 wraps rather than building an unbounded schedule, so a badly wrong
  device clock cannot hang the page.
- 400 runs build in 35ms cold; cached lookups are free.

Tested: runs 1 to 6 byte-identical to what aired, and still identical after the pool is
padded to 100; determinism across fresh module loads and out-of-order access; difficulty
never falls within a run; a recycled chart is at least 6 runs old; pool sizes 3 to 49;
a retired puzzle warns and drops without breaking the deal; Playwright across five
simulated days in both themes at 390px with the rendered chart matched against the
dealer's prediction; option ramp still 4,4,4,6.

The patch touches only the dealer block. Everything after it is byte-identical to the
deployed file.
